### N01 · 같은 무기를 다시 선택해도 발사 대기시간을 줄인다

근거: `Source/CrashRumble/Character/CRCharacter.cpp:1681-1698`, `Source/CrashRumble/Weapon/CRWeaponComponent.cpp:306`, `:402-427`.

`SetSlotHeld(..., true)`는 매번 `EquipSlotWeapon()` → `Equip()`을 호출한다. `Equip()`은 무기가 같아도 `NextFireTime = Min(NextFireTime, WeaponClock + 0.1)`을 실행한다. 기존에도 전환 때 대기시간 단축은 있었지만, 이번 변경으로 일반 공격 버튼을 다시 누르는 것만으로 이 경로를 탄다. 따라서 0.6초 같은 긴 발사 간격을 설정해도 버튼을 빠르게 떼었다 누르고 0.1초 이상 유지하면 훨씬 빨리 재발사한다. 공격속도·업그레이드로 정한 간격을 입력 빈도로 우회한다.

제안: 동일 무기 재장착을 입력 시작 경로에서 피하고, 실제 무기 전환도 쿨다운 정책을 명시한다. 장비 외형 갱신과 발사 대기시간 초기화를 분리한다.

검증: 레이저 간격을 1초로 두고 길게 누른 경우와 0.15~0.2초 간격으로 재클릭한 경우의 실제 발사 수를 비교한다. 좌·우 교대 입력과 장비 변경도 함께 확인한다.

### N02 · 풀에 돌아간 캐릭터의 화상이 다음 생명까지 남는다

근거: `Source/CrashRumble/Character/CRCharacter.cpp:1067-1125`, `Source/CrashRumble/GAS/CRCombat.cpp:214-243`, `Source/CrashRumble/GAS/CRAttributeSet.cpp:24-45`.

이번에 duration/periodic 방식의 `UCRBurnEffect`가 추가됐다. 그러나 캐릭터 반납·재획득은 타이머·사망 태그·체력만 정리하고 활성 GameplayEffect를 제거하지 않는다. 풀 반납이 ASC를 파괴하거나 비활성화하지도 않는다. `PostGameplayEffectExecute()`에는 풀 여부 검사가 없다. 살아 있는 불탄 몬스터를 `CRWave stop`으로 반납하거나 화상 지속시간보다 빨리 사체를 반납한 뒤 같은 액터를 재사용하면, 이전 화상이 새 체력에 피해를 줄 수 있다. 역할이 바뀐 도플갱어에도 이어질 수 있다.

제안: 풀 반납 때 해당 생명에 속한 화상 등 임시 효과를 제거한다. 영구 효과가 추가될 것을 고려해 제거 범위는 명시한다. 일반 부활(`Revive`)의 지속 효과 정책도 함께 정한다.

검증: 화상 시간을 길게 설정하고 몬스터를 불태운 뒤 웨이브 중지·재시작을 반복한다. 같은 액터 재사용 직후 활성 효과 수와 HP를 기록한다. 풀 안에 있는 동안에도 피해 콜백이 발생하는지 확인한다. **ASC 주기 실행과 실제 재사용 타이밍은 엔진 실행으로 확인해야 한다.**

### N03 · 화상 갱신이 주기 타이머를 매번 처음부터 시작한다

근거: `Source/CrashRumble/GAS/CRCombat.cpp:229-243`, `Source/CrashRumble/GAS/CRDamageEffect.cpp:20-27`, `Source/CrashRumble/GAS/CRDamageEffect.h:27`.

화상을 갱신할 때 기존 효과를 제거하고 새 효과를 적용한다. 주기는 0.5초이며 적용 즉시 실행은 꺼져 있다. 0.5초 안에 다시 불을 맞으면 첫 틱 전에 제거된다. 예를 들어 기본 불 간격 0.6초에 플레이어 공격속도 +50%를 적용하면 약 0.4초마다 갱신하므로, 계속 공격할 동안 화상 피해가 나오지 않고 공격을 멈춘 뒤에야 발생한다. 플레이어와 도플갱어의 불이 엇갈려 들어와도 가능하다. 직접 타격 피해는 별도로 남는다.

제안: 기존 효과의 남은 시간·피해를 갱신하되 다음 주기 실행 시점을 보존한다. 스택/refresh 정책을 사용한다면 period reset 여부를 명시하고 확인한다.

엔진 소스 추가 확인: 로컬 UE 5.8의 `Engine/Plugins/Runtime/GameplayAbilities/Source/GameplayAbilities/Private/AbilitySystemComponent.cpp:1292`는 instigator가 null이면 같은 효과 클래스 전체를 제거 대상으로 삼는다. 같은 디렉터리의 `GameplayEffect.cpp:4495-4507`은 새 효과 적용 때 월드 TimerManager에 새 주기 타이머를 등록한다. 따라서 기존 화상 제거 → 새 타이머 등록 경로를 소스로 확인했다. 플레이 검증은 별도다.

검증: 공격속도 0%와 +50%에서 같은 대상에게 5초 이상 불을 연사하고 직접 피해와 주기 피해를 분리해 기록한다. 불을 중단하기 전에도 0.5초 단위 화상이 발생해야 한다.

### N04 · 고정 보폭 7이 설정 가능한 생성 비율과 충돌한다

근거: `Source/CrashRumble/Core/CRWaveSubsystem.cpp:149-168`, `Source/CrashRumble/Core/CRTuningSettings.cpp:507-509`.

선택 인덱스가 `(SpawnSerial++ * 7) % TotalWeight`이다. 기본 비율 5:3:2에서는 순회하지만, 옵션창에서 가능한 5:1:1(합 7)은 인덱스가 항상 0이라 칼만 생성한다. 5:5:4(합 14)도 두 인덱스만 순회한다. 비율을 바꾸면 무기 구성이 설정과 달라진다.

제안: `SpawnSerial % TotalWeight`로 모든 가중 슬롯을 순회하거나, 가중 셔플/가중 난수 선택을 사용한다. 세 비율이 전부 0인 경우에도 별도 정책을 둔다.

검증: 선택식만 PowerShell로 70회 실행해 5:1:1에서 실제 결과가 **70/0/0**임을 확인했다(기대 50/10/10). UE 스폰을 실행한 결과는 아니다. 수정 후 합이 14·21인 경우도 포함해 분배를 확인한다.

### N05 · 저장 override 이름 목록이 현재 저장 내용과 동기화되지 않는다

근거: `Source/CrashRumble/Core/CRTuningSubsystem.cpp:51-59`, `:73-88`, `:93-107`, `:133-148`.

`SavedNames`는 `Load()`에서 추가되고 전체 초기화에서만 비워진다. 사용자가 개별 항목을 JSON 기본값으로 되돌려 `Save()`하면 파일에서는 override가 빠지지만 이름은 남는다. 이후 JSON 핫 리로드는 `SavedNames.Contains()` 때문에 현재 값이 이전 기본값과 같아도 새 기본값을 반영하지 않는다. 종료 때 저장하면 구 기본값이 다시 override로 저장되어 다음 실행에도 새 JSON 값을 가린다.

재현: `SwordDamage`를 기본값과 다른 값으로 저장 → 재실행 → `cr.Tune SwordDamage 25`로 현재 기본값(종료 커밋 기준 25)에 복귀·저장 → `weapons.json`의 기본 피해를 30으로 변경 → 핫 리로드. 기대는 30, 코드 경로상 25에 남는다. 실제 사용 중인 JSON 기본값이 다르면 그 값으로 복귀시킨다.

제안: 저장/개별 값 변경 시 override 목록도 현재 유효 상태와 동기화한다. `Save()`의 diff 정책과 `ApplyJsonDefaults()`의 사용자 수정 판정이 같은 기준을 사용하도록 한다.

### N06 · 패시브 런처의 큐 처리량보다 빠른 요청을 제한하지 않는다

근거: `Source/CrashRumble/Weapon/CRWeaponComponent.cpp:963-988`, `:990-1002`, `Source/CrashRumble/Character/CRLoadoutComponent.cpp:507-516`, `Content/GameData/upgrades.json`의 `plauncher_count`, `plauncher_rate`.

새 큐는 이미 대기 중인 마지막 발 뒤에 다음 요청 전체를 붙인다. 일반 발사 간격은 발당 0.12초다. 패시브 자동 다연장 3단계는 4발이고 자동 런처 가속 3단계는 간격에 0.8³을 곱한다. 여기에 옵션창에서 가능한 공격속도 증가를 적용하면 요청 주기가 4발 처리시간(0.48초)보다 짧아질 수 있다. 가까운 적이 계속 있는 동안 큐 길이·마지막 발사 예정 시각이 계속 늘어나며, 패시브를 빼도 그동안 쌓인 발사가 이어진다. 새 구조에 큐 길이/대기시간 상한이나 장비 해제 취소가 없다.

제안: 최대 대기 요청 수를 두거나 진행 중인 salvo에는 새 요청을 합치지 않는 등 처리 정책을 둔다. 장비 해제·풀 반납 때 어느 요청을 취소할지도 정한다. 단순 무제한 append는 피한다.

검증: 자동 런처 다연장·가속을 최대 강화하고 공격속도 +500%에서 근처 적을 유지한다. 30초 동안 `PendingMissiles.Num()`과 마지막 예정 시각을 기록하고 장비를 해제한다. 큐가 일정 범위에 머물고 해제 정책대로 종료되어야 한다. 기본 설정만으로 무한 증가한다고 주장하는 항목은 아니다.

## 이전 리뷰 수정 확인

- R01: `BlockRegenVisitPerFrame`과 커서가 도입되어 재생 성공 수 외에 검사 수를 제한한다. 성능 수치를 다시 측정하지는 않았다.
- R02: 숫자 변환·구조물 범위·생성 개수 제한이 추가됐다. JSON 전체 크기 등 모든 입력 비용을 제한한다는 의미는 아니다.
- R03/R06: 최초 재탐색 시각 분산과 DPS 10초 기록 보관을 확인했다. 공간 인덱스 보류는 이전 Claude의 측정 근거를 유지한다.
- R05: 벤치 시작 조건 스냅샷, 튜닝 변경 표시, 메타데이터 저장을 확인했다. seed 고정은 여전히 보류다.
- R07/R08: 대여 집합 검사와 무기 외형 지연 생성을 확인했다.
- R10/D: JSON 데이터 기본값과 업그레이드가 도입됐다. 이번에는 새 동작의 정합성을 검토했다. N05는 그 경로에서 발생한다.

## 검토 범위와 한계

장비/인벤토리, 캐릭터 생명주기·도플갱어, 웨이브·골드, 무기·투사체·미사일, GAS 피해/화상, JSON 기본값/업그레이드, 컨트롤러·HUD·튜닝 UI, 이전 수정 diff를 읽었다. 아트·바이너리 에셋의 시각 품질과 실제 성능·패키징 결과는 검증하지 않았다. `git diff --check a7ded15 c7c550a`는 통과했다. 이 검사는 C++ 컴파일·런타임 검증을 대신하지 않는다.

데이터 보조 검사: `Content/GameData/*.json` 5개와 `Content/MapData/ingame.json`을 PowerShell `ConvertFrom-Json`으로 파싱했다. 업그레이드 39개에서 중복 ID와 존재하지 않는 선행 ID는 없었다. UE 파서의 모든 형식·수치 검증을 대신하는 검사는 아니다.

## Claude에게 요청

1. 동일 종료 커밋의 소스에서 N01~N06을 각각 **동의 / 부분 동의 / 반박 / 실행 확인 필요**로 판정한다. 반박에는 코드 근거를 붙인다.

4. 정적 추론·실제 실행·기존 문서 인용을 구분하고, 추가 발견은 별도 ID로 쓴다.
5. 결과는 별도 Markdown으로 남기고 원 리뷰는 보존한다.
