# CrashRumble 구조·성능 리뷰

작성일: 2026-10-29 (Asia/Seoul)

리뷰 범위: **`8345b06` 최초 프로젝트 생성부터 `a7ded15` 벤치마크 진행 상황 기록까지, 양 끝 포함 29개 커밋**. 전체 해시는 [리뷰 색인](README.md)에 기록했다. 작업 시작 시 추적 파일 변경은 없었다.

## 판단 기준과 기존 구현

- P1: 큰 프레임 지연이나 비정상 입력에 따른 정지를 먼저 방지할 항목.
- P2: 확장성·지속 사용 성능·측정 신뢰도를 개선할 항목.
- P3: 변경 빈도와 측정 결과를 보고 진행할 항목.
- '확인'은 소스에서 확인한 동작, '제안'은 아직 구현·측정하지 않은 개선이다. 심각도는 실제 장애 재현 결과가 아닌 정적 리뷰 우선순위다.

이미 있는 액터 풀, VFX 고정 버퍼·ISM, 시각 LOD, 튜닝 레지스트리·SaveGame, 에셋용 `UCRGameSettings`, 외형용 `UCRCharacterAppearance`, JSON 맵을 활용하는 방향이 적합하다. 블럭 붕괴 검사는 기본 경로에서 이미 Tick으로 합쳐졌으므로 '타격마다 전체 검사'를 현재 문제로 중복 지적하지 않는다.

## 개선 항목

### R01 · P1 · 재생 예산이 큐 탐색 비용을 제한하지 않음 [확인]

근거: `Source/CrashRumble/Map/CRBlockArena.cpp:804-841`, 특히 813~831행. 관련 이력: `c521149` 이후 블럭 시스템.

`BlockRegenPerFrame`은 재생 성공 시에만 감소한다. 아직 시간이 안 되었거나 캐릭터·이웃 조건 때문에 연기된 셀은 예산을 쓰지 않는다. 따라서 큰 크레이터 이후 수천 셀이 대기하면 매 프레임 큐 전체를 순회할 수 있고, 기한이 지난 셀은 다수의 overlap 검사까지 수행할 수 있다.

제안: 재생 성공 예산과 별개로 검사 셀 수/시간 예산을 두고 커서를 유지한다. 이후 필요하면 기한별 큐로 바꾸되 같은 셀의 재예약 중복을 막는다. 대기 큐를 처리할 때마다 배열 앞에서 삭제하는 방식은 피한다.

검증: 큰 크레이터와 재생 위치를 가리는 캐릭터를 배치하고 큐 길이, 방문 셀 수, overlap 수, `CR_ArenaTick` p95/p99를 비교한다. 장기간 미처리되는 셀이 없어야 한다.

### R02 · P1 · 맵 크기 제한과 별개로 구조물 확장 루프는 무제한 [확인]

근거: `Map/CRMapFile.cpp:189-210`, `:333-347`, `:425-435`, `:479-497` (이 문서에서 축약한 소스 경로의 루트는 `Source/CrashRumble/`). 관련 이력: `c521149`, `7b6b49d`.

최종 격자는 제한하지만 `fill`의 from/to, 피라미드 base, `dummy_grid` 범위는 입력 범위를 그대로 순회한다. `FBuilder::Set`의 경계 검사는 루프 안에서 수행하므로 맵 밖 좌표도 계산 비용을 낸다. `dummy_grid`는 격자 밖 오브젝트 사양도 계속 추가한다. JSON 작성 실수만으로도 동기 로드/핫 리로드가 오래 멈출 수 있다.

제안: 확장 전에 좌표를 격자와 교차시키고 구조물별 최대 작업량·전체 오브젝트 수를 검증한다. 범위가 너무 크면 구체적인 필드 오류를 반환한다. JSON 숫자의 타입·유한성·정수 변환 범위도 검증한다.

검증: 맵 밖으로 크게 벗어난 fill, 큰 base, 큰 dummy_grid를 넣어 제한 시간 내 거부되는지 확인한다. 기존 arena/training/bench 맵 결과는 같아야 한다.

### R03 · P2 · 적 재탐색은 빈도를 낮췄지만 전체 목록 검색 [확인]

근거: `Core/CRTargetSpawner.cpp:265-288`, `Character/CRCharacter.cpp:877-885`, `:934-941`. 관련 이력: `e14d2e2` 팀 전투 이후.

유닛별 약 0.2~0.4초 재탐색은 이미 적용되어 있다. 다만 각 검색은 아군까지 포함한 `ActiveTargets` 전체를 돈다. 전체가 한 번씩 재탐색하는 비용은 대략 O(N²)이며, 생성 직후에는 모두 타이머가 0이어서 첫 검색이 몰릴 수 있다.

제안: 우선 팀별 활성 목록과 프레임당 재탐색 예산을 도입하고 최초 검색도 분산한다. 규모가 더 커지면 공간 그리드를 검토한다. 정확한 최근접 적이 필요하면 인접 셀만 보고 끝내지 말고 탐색 범위 확장/종료 조건을 정의한다.

검증: 50/100/300 vs 동수에서 `CR_FindNearestEnemy` 누적 시간과 첫 교전 프레임을 비교한다. 사망·풀 반납·재등장 후 표적 무효화도 확인한다. 시각 LOD는 이동/AI 계산을 줄이지 않으므로 이동 병목은 별도로 측정한다.

### R04 · P2 · VFX·낙하 블럭 경로에 전체 렌더 상태 갱신이 남음 [확인 / 효과는 측정 필요]

근거: `Feedback/CRFxSubsystem.cpp:817-889`, `Map/CRBlockArena.cpp:774-801`. 관련 이력: `17fb1c7`, `c521149`; 비교 기준 `8bed9c8`.

정적 블럭은 기본 경로에서 `MarkRenderStateDirty`를 피하지만 도형·블롭 그림자·낙하 블럭은 `UpdateBounds`와 `MarkRenderStateDirty`를 호출한다. 블롭은 매 Tick 처리된다. 파괴된 정적 블럭을 100000cm 아래로 옮기는 방식도 컴포넌트 경계에 영향을 줄 수 있어 함께 확인할 가치가 있다.

제안: Unreal Insights로 해당 갱신과 인스턴스 변경 비용을 분리 측정한다. 부분 변경 경로를 사용할 수 있는지 실험하고, 정적 지형은 청크별 ISM과 안정적인 셀→청크/인스턴스 매핑을 검토한다. VFX는 활성 범위에 맞는 경계 관리 방식을 비교한다.

검증: 렌더 상태 갱신 수, bounds 시간, 게임/렌더 스레드 p95/p99, 화면 밖 컬링을 비교한다. 카메라 이동 시 이펙트가 사라지지 않고 지형 충돌·재생·맵 재로드가 같아야 한다. **엔진 내부 동작을 확인하지 않은 채 dirty 호출만 일괄 삭제해서는 안 된다.**

### R05 · P2 · 벤치마크 조건이 측정 도중 바뀔 수 있고 결과에 충분히 남지 않음 [확인]

근거: `Core/CRBenchmark.cpp:61-108`, `:179-194`, `:222-240`, `:262-311`. 관련 이력: `8bed9c8` ~ `30e9b79`.

진형은 시작 때 읽지만 측정 시간은 Tick에서, trace 옵션은 측정 시작 때, legacy 표시는 결과 작성 때 현재 튜닝을 읽는다. 전투 수치도 게임 코드가 현재 튜닝을 읽으므로 중간 변경 시 한 실행 안에 조건이 섞인다. 출력에는 커밋·전체 설정·seed·빌드 환경이 없어 결과만으로 재현하기 어렵다.

제안: 실행 시작 시 유효 설정을 스냅샷하고 진행 중 관련 튜닝 변경을 제한하거나 실행을 무효로 표시한다. 프리셋 ID, 커밋, 맵 파일 해시, 유효 진형 수치, 실제 생성 수, seed, 해상도·빌드·하드웨어·trace 여부를 별도 메타데이터로 저장한다. seed를 기록하려면 전투·재생 등의 난수를 명시적인 스트림으로 전달해야 한다.

검증: 같은 프리셋으로 3회 이상 비교하고 진행 중 옵션 변경이 일관되게 거부/표시되는지 확인한다. trace 켠 실행과 끈 실행을 섞지 않는다. `PLAN.md`의 69.6→86.8 FPS는 기존 기록이며 이번 리뷰에서 재현한 수치가 아니다.

### R06 · P2 · 연속 DPS 측정 로그가 계속 증가함 [확인]

근거: `Character/CRCharacter.cpp:229-246`, `:1207-1222`. 관련 이력: `7b6b49d`.

피격마다 로그를 추가하고 긴 무피격 공백일 때만 초기화한다. 계속 공격하면 오래된 로그가 남으며 `GetDps()`는 최근 윈도우 합을 위해 전체 기록을 돈다. 훈련장 장시간 자동 사격에서 메모리와 조회 시간이 증가한다.

제안: 누적 피해는 별도 합계로 유지하고 윈도우 로그는 오래된 항목을 만료시키는 큐/링 버퍼로 관리한다. DpsWindow 확대 시 과거 기록 복구가 필요한지 정책을 정하고 최대 지원 윈도우만큼 보관한다.

검증: 30분 연속 사격에서 기록 수와 조회 시간이 안정적으로 유지되는지, 초기 0.5초 분모·무피격 초기화·윈도우 변경 결과가 의도와 같은지 확인한다.

### R07 · P2 · 풀의 중복 반납·소유권 검사가 없음 [확인, 현재 호출부에서 발생했는지는 미확인]

근거: `Core/CRActorPool.cpp:11-58`. 관련 이력: 이름 변경 전 `4a72846`, `6401943`부터 이어진 풀.

같은 Actor를 두 번 `Release`하면 대기 목록에 두 번 들어간다. 이후 연속 `Acquire`가 같은 객체를 두 번 반환할 수 있으며 active count도 실제 상태와 달라진다. 다른 월드의 액터나 풀에 속하지 않은 액터도 유효성 검사만 통과하면 받아들인다.

제안: 풀 소유 월드·지원 클래스와 대여 상태를 기록하고 반납은 멱등적으로 처리한다. 새 객체 생성/대여/반납 상태 전이는 한 경로에서 관리한다. 클래스별 prewarm·상한·초과 정책도 설정으로 분리할 수 있다.

검증: 중복 반납 뒤 두 번 대여, 다른 월드 객체 반납, 파괴된 객체 재대여를 검사한다. 두 활성 대여가 같은 Actor를 공유하면 안 된다. 실제 일반 플레이에서 이미 발생한 버그라고 단정하지 않는다.

### R08 · P2 · 모든 캐릭터가 미사용 무기 외형까지 생성 [확인]

근거: `Character/CRCharacter.cpp:154`, `Weapon/CRWeaponComponent.cpp:76-90`, `:130-214`. 관련 이력: `4a72846` 전투부터 `17fb1c7` 무기 확장.

초기화 시 칼·레이저·투사체·번개·미사일·불꽃 외형과 빔·총구 광원 컴포넌트를 모두 만든다. 무기 하나만 쓰는 팀 유닛과 비무장 허수아비도 생성 비용과 숨겨진 컴포넌트를 보유한다. 풀링은 재생성 비용을 줄이지만 이 보유량은 줄이지 않는다.

제안: 장착/발사 시 필요한 외형을 지연 생성하거나 역할별 허용 무기 집합을 전달한다. 무기 전환이 잦은 플레이어는 캐시하고, 고정 무기 AI는 필요한 것만 유지한다. 로딩 화면에서 선택적으로 prewarm한다.

검증: 600유닛의 컴포넌트 수, 메모리, 최초 스폰 지연과 첫 발사 지연을 비교한다. 풀 재사용·무기 교체 시 이전 빔/총구 광원이 남지 않아야 한다.

### R09 · P2 · 캐릭터·컨트롤러의 책임 분리 [구조 제안]

근거: `Character/CRCharacter.cpp:521-580`의 Tick 조합, `:871-953` 전투 AI, `:1110-1165` 외형 조립; `Core/CRPlayerController.cpp:94-424` 벤치·시연·미리보기, `:514-622` 입력 생성·바인딩, `:643-665` 맵 편집. 관련 이력: 캐릭터·모드·맵·미리보기 확장 전반.

캐릭터 약 1524행에 생명주기, AI, 훈련장 측정, 파츠 애니메이션이 모여 있다. 컨트롤러 약 999행에도 입력, 도구 명령, 효과 미리보기, 옵션 UI가 섞여 있다. 행 수 자체보다 역할별 상태와 변경 이유가 다른 점이 분리 근거다.

제안: 캐릭터는 생명주기·GAS 연결을 조정하고 AI, 시각 표현, 훈련장 측정은 별도 C++ 객체/컴포넌트로 옮긴다. 컨트롤러의 미리보기·시연·벤치 명령은 도구 서비스로 분리한다. 맵 액터도 격자 데이터·붕괴/재생 계산·ISM 표시·파일 감시 경계를 나눈다. 모든 계산을 Tick 컴포넌트로 늘리기보다 기존 Tick에서 명시적으로 호출하는 형태부터 시작한다.

검증: 풀 acquire/release, 사망·리스폰, 무기 전환, 맵 재로드, 옵션 변경 순서를 고정한 회귀 시나리오로 비교한다. 이동 성능 변경과 책임 분리를 한 번에 수행하지 않는다.

### R10 · P2 · 수치의 원본과 튜닝/UI 정의를 분리하고 안정적인 ID 사용 [구조·데이터 제안]
